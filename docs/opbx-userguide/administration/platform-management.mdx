# Platform Management

:::danger Platform Owners/Operators Only
This section applies only to people who operate the OPBX deployment. Organization users (Owner, PBX Admin, PBX User, Reporter, Supervisor) cannot open Platform Management. If you administer one organization, see [Organization Settings](/administration) instead.
:::

Platform Management is a cross-tenant console for the team that hosts OPBX for one or more customer organizations. It appears in the sidebar as **Platform Management** for platform managers only.

## Pages

| Sidebar item | Path | What it is for |
|--------------|------|----------------|
| Dashboard | `/ui/platform/dashboard` | Counts across all organizations (organizations by status, users, extensions, active calls) |
| Organizations | `/ui/platform/organizations` | List, open, edit, suspend, reactivate and delete organizations; **Operate As** |
| Users | `/ui/platform/users` | Users in every organization; create, edit, platform-manager flag, password, delete |
| Audit Log | `/ui/platform/audit-log` | Record of platform actions |
| Platform Status | `/ui/platform/status` | Health of every OPBX component, with a 24-hour history |

The public status page at `/status` is separate. It needs no login and shows only coarse group health. See [Public status page](#public-status-page).

## Access Requirements

The `is_platform_manager` flag on a user account grants access. It is separate from the organization role.

The flag is set with the `opbx:set-platform-manager {email}` command on the server, or by an existing platform manager through the Users page. `opbx:revoke-platform-manager {email}` removes it.

:::caution
The last platform manager cannot be revoked. Create and confirm a second one first.
:::

## Organizations

### Viewing and creating

The Organizations list shows every organization with its status and details. The platform console has **no** action to create an organization. New organizations are created by self-registration or Auth0 sign-up, and the first platform manager can be created with `opbx:create-platform-manager`.

### Status: Active, Suspended, Deleted

| Status | Effect |
|--------|--------|
| **Active** | Normal operation |
| **Suspended** | Every request from that organization's users (API and web) is refused with HTTP 403 "Your organization has been suspended." Data is kept. Platform managers are not blocked, so they can still open and reactivate the organization |
| **Deleted** | The organization is removed with its data (see below) |

To suspend or reactivate, use the status control on the organization. Suspended organizations can be reactivated at any time.

{/* SCREENSHOT: platform-org-status — Organizations list with one Suspended row (yellow status badge) and the status control open */}

### Deleting an organization

Deleting an organization removes its configuration and data, including extensions, ring groups, business hours, phone numbers and call logs, and revokes the users' API tokens. The delete is refused in these cases:

- **Any user in the organization is a platform manager.** Revoke their platform-manager flag first. The error names the rule.

:::danger
Deleting an organization cannot be undone. Suspend first, take a database backup, and confirm with the customer.
:::

{/* SCREENSHOT: platform-org-delete-blocked — Organization delete refused because one user is a platform manager */}

### Operate As an organization

Platform managers can act as the **Owner** of an active organization, to reproduce a customer's problem without their password.

1. Open **Platform Management → Organizations**.
2. Click **Operate As** on the organization's row. You can enter a reason, which is stored on the audit entry.
3. Work as that organization's Owner. A yellow banner stays at the top of every page.
4. Click **Exit organization** in the banner to return to your own platform identity.

How it works:

- The SPA attaches an `X-Operate-As-Organization` header to every API call during the session. There is no server-side session to time out; the session ends when you exit, log out, or your token expires.
- Only a real platform manager can start a session. API keys and ordinary users are refused.
- Only **active** organizations can be targeted. Suspended or deleted organizations are refused.
- Starting and stopping are both written to the platform audit log as `operate_as.started` and `operate_as.stopped`.

:::warning Full Owner access
While operating as an organization you can change anything its Owner can, including users, routing and Cloudonix settings. Exit as soon as you are done.
:::

## Users

The Users page lists users across all organizations. Platform managers can:

- create a user in a chosen organization;
- edit a user, including the platform-manager flag;
- set a user's password;
- preview and delete a user.

### Deleting a user

Before the delete is sent, a **Delete User** dialog shows what it will change. The same impact preview is used by organization admins (see [User Management](/modules/user-management)): the user's extensions are kept but unassigned, memberships are removed, and routes that pointed at those extensions become "Destination unavailable". Confirm only after reading the list.

Platform-level guards:

| Guard | Result |
|-------|--------|
| Deleting your own account | Refused: "You cannot delete your own account." |
| Deleting the last owner of an organization | Refused: "Cannot delete the last owner of an organization." |
| Revoking the last platform manager | Refused: "Cannot revoke the last platform manager." |

## Platform Status

The Platform Status page shows every OPBX component, its current status, and what happened over the last 24 hours.

{/* SCREENSHOT: platform-status-overview — Platform Status page: component cards (green/amber/red) and 24h status strips */}

### Components

| Component | What is checked |
|-----------|-----------------|
| API / app | Application is answering; PHP and Laravel versions |
| MySQL (main) and MySQL (CDR archive) | Query and server version. The archive is the warm CDR tier |
| Redis | Ping and memory use |
| SeaweedFS | Both buckets reachable (recordings and CDR archive) |
| Queue | Pending and failed jobs across the queues |
| Scheduler | Age of the heartbeat written by the scheduled health check |
| ACD worker, AMD worker, Dialer worker | Their health endpoints |
| Soketi (real-time updates) | Readiness endpoint |
| MCP server | Health endpoint |
| Loki, Grafana | Only when the `logs` profile is running |
| Cloudonix API | A lightweight request to the Cloudonix API |

Each check reports **ok** (green), **degraded** (amber) or **down** (red), with the latency and a short detail.

### How status is decided

Thresholds come from `config/platform_status.php`:

| Check | Degraded (amber) | Down (red) |
|-------|------------------|------------|
| HTTP probes (workers, Soketi, MCP, SeaweedFS, Loki, Grafana) | Response slower than 1500 ms | Unreachable (timeout or refused) or an error HTTP status. An optional service that is not running (Loki, Grafana without the `logs` profile) shows "unknown" instead |
| Queue | More than 500 pending jobs, or 50 or more failed jobs | Never; the queue check reports degraded at most |
| Scheduler heartbeat | Last run 1 to 3 minutes ago | Last run more than 3 minutes ago (also when it has never run) |
| Cloudonix API | Three consecutive checks with no fast answer (slow or no answer), not all of them lost | Three consecutive checks with no answer at all |

A Cloudonix answer counts as slow when it takes longer than 3000 ms. A check fails when no answer arrives within 5 s.

Cloudonix is an external Internet service, so a single slow or lost request never changes its status. Only the third consecutive bad check does.

The scheduler check is the only one that depends on the schedule itself. It stays "unknown" until the first scheduled run after installation. A manual **Check now** does not refresh the scheduler heartbeat.

### History and checks

- The checks run every minute from the scheduler and are stored.
- The page shows a 24-hour strip per component. Hover a segment to see its time and status.
- The page refreshes every 30 seconds while the tab is visible.
- **Check now** runs every check immediately. It is rate-limited to 6 requests per minute.
- History is kept for `PLATFORM_HEALTH_RETENTION_HOURS` (default 24) and pruned by the daily `model:prune` run.

No email or other notification is sent. Someone must watch the page.

## Public status page

`/status` is a public page that needs no login. It is linked from the public home page navigation and the footer.

It shows six groups, each the worst status of its components:

| Group | Components |
|-------|------------|
| Web portal & API | API, MySQL (main), Redis |
| Call routing | API, Cloudonix |
| Call queues | ACD worker, queue |
| Auto dialer & voicemail detection | Dialer worker, AMD worker |
| Recordings & storage | SeaweedFS, MySQL (CDR archive) |
| Real-time updates | Soketi |

The banner reads **All systems operational**, **Partial outage** or **Major outage**. The page shows a six-hour strip per group.

Internal components (scheduler, Loki, Grafana, MCP server) and all details (versions, latency, hostnames, error messages) are never shown on the public page. The data comes from `GET /api/v1/public/status`, cached for 30 seconds.

## Audit Logs

Every platform action is recorded with:

| Field | Description |
|-------|-------------|
| Timestamp | When it happened |
| Actor | The platform manager who did it |
| Action | For example `operate_as.started` or `operate_as.stopped` |
| Target | The organization or user affected |

Audit entries are kept for `RETENTION_PLATFORM_AUDIT_LOGS_DAYS` (default 365) and then pruned. See [Data retention](/data-models/configuration/index#data-retention).

## Cross-tenant call data

The Platform API has a read-only **CDR archive** endpoint that lists warm-tier call records (6 to 12 months old) for all organizations. The web console does not show it. See [Call Logs](/modules/call-logs#retention-and-archive).
